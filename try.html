Path A — Starting from scratch

~2-3 hours · greenfield

You have an idea — a tool, a small SaaS, a video game, a TTRPG companion app, a niche utility. You want it to actually exist by tonight. Here's the conversation:

01
Open your AI assistant. Claude Code, Cursor, VS Code with GitHub Copilot Chat, Aider, Windsurf — whatever you already use. Make a new empty folder somewhere on your machine and point the assistant at it (open the folder in your editor, or cd into it in the CLI version).
02
Tell it what you want to build. Two or three sentences, plain language, no jargon. Something like:
Paste this, edited for your ideaI want to build a small tool that lets me track which board games I've played with friends, what we thought, and which ones we want to play next. It should work on my phone, sync across devices, and not require an account to start.
03
Ask it to use PragmaWorks. This is the move that turns a regular AI conversation into a disciplined one:
Paste this verbatimUse the PragmaWorks methodology to bootstrap this project. Find pragmaworks on npm, install what you need, generate the specification first, set up the ForgeCraft cascade, then build the project under that discipline. Before you start, ask me 2-3 clarifying questions about scope and tech stack — pick the stack yourself if I have no preference.
04
Answer its questions briefly. The assistant will ask things like: "What's the smallest version that's useful (the MVP)?" "Any tech stack preference, or should I choose?" "Local-only or hosted?" Answer in one or two sentences each. Don't overthink it — the spec it builds will absorb your answers and ask follow-ups if anything is unclear.
05
Sit back. The assistant works. It writes the specification (use cases, behavioral contracts, architecture decisions, AI behavioral rules). It generates the code from the spec. It writes the tests. It sets up the deployment scripts. You do not write code. You do not type CLI commands. Tier 1 (specification), Tier 2 (test harness), and Tier 3 (deployment) are done automatically.
06
Optional — verify the harness yourself. If you're technical and want to feel the discipline working, ask the assistant:
Optional follow-upRun the harness end-to-end. Show me the test results, take screenshots of the running app, and confirm everything matches the spec.
The assistant will spin up the local app, drive it through the use cases, capture screenshots, compare against the spec, and report back. If anything is off, it will tighten the spec and regenerate — not patch the code.
07
You have a real project. Working code, tests passing, deployable. The whole thing came from a conversation. You can run it locally or push to wherever you deploy. From here you can ask for new features the same way: "Add a leaderboard for players' favorite games." The discipline keeps the second feature from breaking the first.

Path B — You already have a project

~2-4 hours · brownfield

You inherited a codebase. Or you built one over a year and you're not sure what shape it's in. Or you've been using AI assistance for a few months and you suspect things are quietly degrading. Here's the conversation:

01
Open your AI assistant in the project root. Same options as Path A — Claude Code, Cursor, VS Code, etc. Point it at your existing repository.
02
Ask it to audit the project. One prompt:
Paste this verbatimUse PragmaWorks to audit this project. Find pragmaworks on npm, install what you need, run the analysis on a new branch (don't touch main), and generate the initial report as a PDF. Cover structural disciplines, the GS rubric, test coverage, documentation health, and propose a remediation plan I can review before we apply anything.
03
Read the initial report. The assistant generates a PDF. It tells you what your codebase looks like today: which structural disciplines apply (it picks from the standard catalog — SOLID, TDD, hexagonal, layered, clean architecture, etc.), what scores it gets on each, the seven GS properties scored 0-2 with evidence, where documentation has rotted, what the test pyramid actually looks like, and where the AI sees the most leverage for improvement.
04
Approve the plan, or modify it. The remediation plan is in the report. Say something like:
Paste thisThe plan looks right. Apply it on the same branch. Pause before any change that would touch the database schema or the public API — ask me first on those.
You set the boundaries. The assistant works through the plan one item at a time, generating spec changes, applying remediations under GS discipline, writing tests for past bugs to prevent regression, and pausing where you said to pause.
05
Get the after-report. Once the work is done, ask:
Paste thisGenerate the after-report. Same format as the initial one, but with a before/after comparison: coverage delta, structural discipline scores delta, GS rubric delta, regression tests added for past bugs, documentation updates. Include charts.
A second PDF lands. Side-by-side numbers. Charts. The receipts of what changed.
06
Optional — commit history study. If you want to know how your team has been operating (PR review density, commit-size distribution, AI-introduced bug signal, who collaborates with whom), ask:
OptionalRun the team-habit analysis on the last 90 days of commit history. Output as a separate PDF with charts.
Useful at the team level. Optional at the individual level.
07
Optional — install Chronicle for living documentation. If you want the project to keep a memory of decisions, prompts, and architectural choices across future AI sessions:
OptionalInstall Chronicle for this project so future sessions inherit the architectural decisions, the spec rationale, and the prompt history we just built.
Particularly worth it if you're going to keep working on this codebase with AI assistance over months. Read more in the Chronicle README if you want detail before deciding.
08
Optional — add a new feature under the same discipline. Now that the spec exists and the harness is wired, adding a feature is conversational:
OptionalAdd [your feature]. Update the spec first, regenerate what needs to change, run the harness, and report back.
This is the moment most people feel what GS actually feels like — a feature added without breaking the existing tests, without ad-hoc patches, without the AI silently creating coupling.
09
Verify it still works. Run the project. Click around. The harness verified the contracts; you verify the experience. This is the judgment layer — what only a human can decide. Welcome.

What you'll have at the end

both paths

Path A — Greenfield

  • A working project. Code, tests, deployment scripts, all derived from a written specification.
  • A specification you can hand to anyone. Use cases, ADRs, behavioral contracts, AI behavioral rules. The next session knows what to do without you in the room.
  • Tier 1, 2, and 3 done. Spec, test harness, deployment infrastructure — all under discipline.
  • An optional path forward. Add features by conversation. Each one tightens the spec.

Path B — Brownfield

  • Two PDF reports. Initial state and final state. Same metrics, side by side. Charts. Receipts.
  • A remediated codebase. Higher scores on the seven properties, regression tests for past bugs, refreshed documentation, better structural discipline.
  • A working harness. Test suite that runs against the running application, not just the code.
  • Optional team-habit report. A separate PDF showing how the team has been operating.
  • Optional Chronicle install. Future sessions inherit what this one learned.
  • Optional new feature. Built under the same discipline so it doesn't break what already works.

Everything happens on a branch. Your main is untouched until you decide to merge. The AI does not type — you do, but only into the chat.
