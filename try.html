Have a conversation. Leave with a real project.

No installs. No configs. No CLI commands you have to type. Open your AI assistant, follow the prompts below, and let it do the work. An afternoon of conversation gets you something you wouldn't have built any other way — under a discipline that keeps the AI from drifting.

Pick the path that fits your situation.

Path A — Starting from scratch

~2-3 hours · greenfield

You have an idea — a tool, a small SaaS, a video game, a TTRPG companion app, a niche utility. You want it to actually exist by tonight. Here's the conversation:

01
Open your AI assistant. Claude Code, Cursor, VS Code with GitHub Copilot Chat, Aider, Windsurf — whatever you already use. Make a new empty folder somewhere on your machine and point the assistant at it (open the folder in your editor, or cd into it in the CLI version).
02
Tell it what you want to build. Two or three sentences, plain language, no jargon. Something like:
Paste this, edited for your ideaI want to build a small tool that lets me track which board games I've played with friends, what we thought, and which ones we want to play next. It should work on my phone, sync across devices, and not require an account to start.
03
Ask it to use PragmaWorks. This is the move that turns a regular AI conversation into a disciplined one:
Paste this verbatimUse the PragmaWorks methodology to bootstrap this project. Find pragmaworks on npm, install what you need, generate the specification first, set up the ForgeCraft cascade, then build the project under that discipline. Before you start, ask me 2-3 clarifying questions about scope and tech stack — pick the stack yourself if I have no preference.

Same step without our tooling. You'd tell the AI directly to set up the doc-first cascade by hand — there's no install, just a folder layout, two git hooks, and a CI step.

Paste thisSet up this empty folder for Generative Specification discipline. No external tooling, just conventions: 1. Create docs/manifest.yaml referencing the canonical schema at github.com/jghiringhelli/forgecraft-mcp/blob/main/templates/docs-manifest.yaml. Pin a version. Set project.name, project.type (api | library | cli | app), release_phase: greenfield, cascade.feat.severity: warning. 2. Scaffold these directories with one-paragraph README stubs: docs/specs/ what we're building (one file per feature) docs/adrs/active/ decisions in force docs/adrs/done/ superseded decisions, kept for history docs/use-cases/ actor + action + outcome (UC-*.md) docs/roadmaps/active/, docs/roadmaps/done/ docs/schemas/ diagrams, JSON Schema, OpenAPI, ER models docs/decisions/ bug-fix one-pagers (YYYY-MM-DD-slug.md) docs/contracts/ NFRs, SLOs, error semantics 3. Add a commit-msg git hook (~10 lines bash) that regex-validates Conventional Commits. 4. Add .claude/hooks/commit-msg-cascade.sh (~30 lines): feat → require any docs/specs/* file is staged fix → require any test file is staged 5. Add a GitHub Actions workflow that runs the same cascade check on PR diff vs base. Severity warning on day 1; flip to error after a quarterly audit shows no gaps. 6. Add CODEOWNERS so a human reviewer is auto-requested. Configure branch protection on main: required PR + checks before merge. Then ask me my project idea and write the first spec at docs/specs/<slug>.md before any code.

That's the whole bootstrap. The PragmaWorks tools just make this ergonomic — the discipline is the folder layout plus two hooks.

04
Answer its questions briefly. The assistant will ask things like: "What's the smallest version that's useful (the MVP)?" "Any tech stack preference, or should I choose?" "Local-only or hosted?" Answer in one or two sentences each. Don't overthink it — the spec it builds will absorb your answers and ask follow-ups if anything is unclear.
05
Sit back. The assistant works. It writes the specification (use cases, behavioral contracts, architecture decisions, AI behavioral rules). It generates the code from the spec. It writes the tests. It sets up the deployment scripts. You do not write code. You do not type CLI commands. Tier 1 (specification), Tier 2 (test harness), and Tier 3 (deployment) are done automatically.
Show the pure-GS variant of this step (no tools)

Without our cascade gates wired in, you'd tell the AI the rule explicitly so it never gets ahead of itself. The whole rule is short:

Paste this before any work beginsWhile you build, follow this cascade strictly. The commit type drives which docs are required: feat: → must touch a file in docs/specs/. Use cases in docs/use-cases/ encouraged. ADR encouraged when a non-obvious architectural choice is made. fix: → must add or change a regression test that proves the bug, BEFORE patching the code. One-pager in docs/decisions/ named YYYY-MM-DD-slug.md encouraged for non-trivial interpretations. refactor: → ADR encouraged when boundaries move. No spec change required. perf | docs | test | chore | ci → no doc cascade required. If you change the public API surface (exports, public types, CLI flags, HTTP routes, MCP tool schemas), spec OR ADR is required regardless of commit type. Order of operations for a feat: 1. Write the spec file first. 2. Write or update the use case. 3. Generate the code. 4. Generate the tests against the use case. 5. Run the tests; tighten the spec if anything is off. Order for a fix: 1. Write the failing regression test FIRST. Confirm it fails. 2. Patch the code. Confirm the test passes. 3. Append a one-paragraph entry to docs/decisions/. If you cannot articulate the spec, ask me before guessing. If you cannot reproduce the bug in a test, say so before patching. End every commit with a one-line summary stating which docs were touched and why — that line is the audit trail.

This is what the cascade gates encode. Pasted as a rule, it works almost as well — you just don't get the "block on push" enforcement.

06
Optional — verify the harness yourself. If you want to feel the discipline working, ask the assistant:
Optional follow-upRun the harness end-to-end. Drive the running app through every use case with Playwright, capture screenshots at each boundary, use multimodal AI to compare each screenshot against the use-case visual postcondition, diff the database state before and after each action, and verify the service-layer logs show the expected sequence. Report the results.
The assistant spins up the local app, drives it through the use cases, takes screenshots, has a vision model compare each screenshot to what the spec says it should look like, runs API endpoint tests via curl, and reports back. If anything is off, it tightens the spec and regenerates — not patches the code. This is what "you stop reading generated code" actually means.
Show the pure-GS variant of this step (no tools)

Same step described in one prompt. The AI drives Playwright, takes screenshots, uses its own vision capabilities to compare each shot to the spec's visual postcondition, and inspects logs and DB state. No orchestration tool required.

Paste thisVerify the harness end-to-end without external orchestration. Use only: Playwright (or your stack's equivalent), the running local app, your own vision capabilities, and direct DB / log access. For each file matching docs/use-cases/UC-*.md: 1. Read the use case. Extract: actor, preconditions, steps, expected visual postcondition, expected database state after each step, expected log lines. 2. Spin up the app on a known port. Reset the database to a known seed. 3. Drive the steps with Playwright. Capture a full-page screenshot after each step. 4. Compare each screenshot against the visual postcondition described in the use case using your own vision. Produce a structured comparison: matched / partially matched / missing / unexpected. Cite the pixel regions you're basing each claim on so I can spot-check. 5. Diff the database state before and after each action. Confirm the expected rows were created / updated / deleted. 6. Tail the application log during the run. Confirm the expected sequence of service-layer events appears. 7. For API-only use cases, run curl or hurl against the endpoints and compare the response body to the contract. Report results as a markdown table: | UC ID | visual | db | logs | overall | first failing line | For any failure, propose a SPEC TIGHTENING — not a code patch. Say which line of which spec or use case needs to be more precise so the next generation gets it right. Tightening the spec is the only legal fix; reaching into the code to patch a symptom is not.

This is the multimodal-AI-as-QA pattern. The PragmaWorks harness automates the loop and persists the test corpus; the prompt gets you 80% of the value once.

07
You have a real project. Working code, tests passing, deployable. The whole thing came from a conversation. You can run it locally or push to wherever you deploy. From here you can ask for new features the same way: "Add a leaderboard for players' favorite games." The discipline keeps the second feature from breaking the first.

Path B — You already have a project

~2-4 hours · brownfield

You inherited a codebase. Or you built one over a year and you're not sure what shape it's in. Or you've been using AI assistance for a few months and you suspect things are quietly degrading. Or you're staring at a migration to a new stack and trying to figure out the safe path. The same flow handles all of these — the audit tells you where the codebase is today, the remediation plan tells you the path forward, and the after-report shows what changed.

01
Open your AI assistant in the project root. Same options as Path A — Claude Code, Cursor, VS Code, etc. Point it at your existing repository.
02
Ask it to audit the project. One prompt:
Paste this verbatimUse PragmaWorks to audit this project. Find pragmaworks on npm, install what you need, run the analysis on a new branch (don't touch main), and generate the initial report as both HTML and PDF. Cover: (1) the seven GS properties — Self-describing, Bounded, Composable, Verifiable, Auditable, Defended, Executable — each scored 0-2 with evidence and a specific path to improve; (2) which structural disciplines apply to this codebase from the catalog (SOLID, TDD, hexagonal, layered, clean architecture, etc.) and how it scores against them; (3) test pyramid coverage; (4) documentation health and staleness; (5) security and logging baseline; (6) a prioritized remediation plan I can review before we apply anything. If this repo already has a CLAUDE.md, agents.md, or similar AI behavioral file, map your output to those locations rather than overriding them.
Show the pure-GS variant of this step (no tools)

Same step without any tooling. You're naming the seven properties and the structural-discipline catalog explicitly so two independent runs land within ±1 — that's what makes the rubric reproducible.

Paste thisAudit this project without any external tooling. Read the codebase, docs, tests, CI config, and git log. Produce a markdown report at reports/audit-initial.md covering: (1) The seven Generative Specification properties, each scored 0/1/2 with cited file:line evidence and one specific path to improve: - Self-describing — specs and ADRs explain intent without needing the author present - Bounded — modules, files, and functions stay within size discipline - Composable — pieces compose without hidden coupling - Verifiable — tests bind specs to behavior - Auditable — commits, ADRs, and decisions trace why each change happened - Defended — security baseline, input validation, secrets handling - Executable — use cases run; specs are not just prose Run the rubric twice on independent passes. Report any divergence above 1 point — that flags a property where the evidence is too thin. (2) Which structural disciplines apply from the catalog (SOLID, TDD, hexagonal, layered, clean architecture, CQRS, ports-and-adapters). Score applicable / partial / n-a with evidence. (3) Documentation health: which docs are stale (no commit in 90+ days while the code beneath them changed), which are missing, which are duplicated. (4) Test pyramid coverage: unit / integration / e2e ratios. Identify the layer most under-served. (5) Security and logging baseline: secrets handling, input validation, what's logged at the trust boundary, where the boundary is. (6) Prioritized remediation plan: 8-15 items, each with effort (S/M/L), risk, and ordering rationale. Do not apply any remediation in this pass. Cite files and line numbers liberally; the report should be reproducible by anyone who can read the codebase.

The PragmaWorks audit packages this prompt with PDF rendering, sister-repo cross-checks, and continuity across runs. The prompt alone gets you the report.

03
Read the initial report. The assistant generates a PDF. It tells you what your codebase looks like today: which structural disciplines apply (it picks from the standard catalog — SOLID, TDD, hexagonal, layered, clean architecture, etc.), what scores it gets on each, the seven GS properties scored 0-2 with evidence, where documentation has rotted, what the test pyramid actually looks like, and where the AI sees the most leverage for improvement.
04
Approve the plan, or modify it. The remediation plan is in the report. Say something like:
Paste thisThe plan looks right. Apply it on the same branch. Pause before any change that would touch the database schema or the public API — ask me first on those.
You set the boundaries. The assistant works through the plan one item at a time, generating spec changes, applying remediations under GS discipline, writing tests for past bugs to prevent regression, and pausing where you said to pause.
Show the pure-GS variant of this step (no tools)

Without our cascade gates, you'd hand the AI the rule before it changes any code. The cascade is what keeps remediation from becoming "AI patches symptoms quietly."

Paste thisApply the remediation plan one item at a time, under this cascade discipline: For every commit: - Use Conventional Commits (feat / fix / refactor / perf / docs / test / chore / ci / revert). - feat → write or update a spec in docs/specs/ BEFORE changing code. Encouraged: matching use case in docs/use-cases/. - fix → write a failing regression test FIRST, confirm it fails, fix the code, confirm it passes. Encouraged: one-pager in docs/decisions/ named YYYY-MM-DD-slug.md. - refactor → if module boundaries move, write an ADR in docs/adrs/active/ before changing code. - Public surface change (exports, public types, CLI flags, HTTP routes) → spec OR ADR required regardless of commit type. Process the remediation list in priority order. Pause and ask me before any of: - Database schema change - Public API change - Anything crossing more than 10 files in a single commit After each item, append a one-line entry to reports/remediation-log.md with: date, commit hash, which docs were touched, what risk you weighed, what test you added. This log is the audit trail; do not skip a row. If the cascade rule and the remediation plan ever conflict, the cascade rule wins — pause and ask me how to reshape the remediation step.

PragmaWorks enforces this at commit/PR time. The prompt encodes the same rule into the AI's working context — close enough for one-shot remediation runs.

Get the after-report. Once the work is done, ask:
Paste thisGenerate the after-report. Same format as the initial one, but with a before/after comparison: coverage delta, structural discipline scores delta, GS rubric delta, regression tests added for past bugs, documentation updates. Include charts.
A second PDF lands. Side-by-side numbers. Charts. The receipts of what changed.

Path C — Joining a project

~1 hour · briefing only, no code changes

You inherited a codebase. Or you're returning after parental leave. Or you're a consultant taking over a system someone else built. You don't need a full audit yet — you need to know what the project is, how it works, and where to start.

01
Open your AI assistant in the project root. Same options as paths A and B.
02
Ask for the onboarding briefing. One prompt:
Paste this verbatim, edit your role/levelUse PragmaWorks to onboard me to this project. Find pragmaworks on npm, install what you need, run the analysis on a new branch (don't touch main), and produce an onboarding briefing as markdown. My role: [frontend / backend / full-stack / data / devops] Experience level: [junior / mid / senior / staff] Module I'm starting on: [optional — leave blank if you don't know yet] The briefing should cover: what this project is in three sentences, the architecture in one diagram, the conventions I must respect, what's surprising about this codebase, 2-3 first-task suggestions sized for my role and experience, and a cheat sheet for getting set up.
03
Read the briefing. Markdown file, 4-8 pages. Designed to be read in 20-30 minutes. Architecture diagram, conventions, what surprises new devs, where to start. Cite the files and lines that support each claim — you can verify by reading.
04
Pick a first task. The briefing ends with 2-3 concrete options sized to your role. Pick one. Start.
05
Optional — for takeover engagements: include team-habit analysis. If you're a consultant or freelancer adopting a codebase from another team, ask:
OptionalInclude team-habit analysis in the briefing. Last 90 days of commit history: PR review density, regression coverage, AI-bug rate, who's been touching what. I want to know who to trust on which areas and where the recent fires were.

Onboarding mode is read-only. It does not propose code changes. If you also want a remediation analysis (what's wrong with this project, what to fix), run Path B separately.

Path D — Moving to a new stack

~3-5 hours · existing project → new project

You're moving an existing system to a new stack, platform, or modernized architecture. Done naively, you reproduce every wart. Done well, you drop unused features, modernize, add NFRs that were missing. This path is the guided version — a three-stage flow: audit the source, refine through a structured conversation, bootstrap the target.

01
Open your AI assistant. You'll need both repos available — the existing source system and an empty target folder for the new system.
02
Start the migration. One prompt:
Paste this verbatimUse PragmaWorks to migrate this project to a new stack. The source system is the current folder. The target folder is at: [absolute path to empty folder]. Find pragmaworks on npm, install what you need. Run the migration in three stages: (1) audit the source and extract a stack-independent specification; (2) walk me through a refinement conversation — what features to drop, what to modernize, what NFRs to add, what tech stack to target; (3) bootstrap the target folder with the refined specification under GS discipline. Pause between stages so I can review.
03
Stage 1 — Source audit (~30 min). The AI extracts what the source system actually does into a stack-independent spec. Behavioral contracts, data models, integration points, use cases. Framework-specific implementation notes are separate from the primary spec.
04
Stage 2 — Refinement conversation (~1 hour). The AI walks you through five passes:
  • Feature triage — for each feature in the source: keep, drop, modernize?
  • Tech stack decision — bundled choice, not piecemeal
  • NFR additions — logging, rate limits, encryption, audit trail
  • Modernization opportunities — polling → WebSocket, homegrown queue → managed, etc.
  • What stays the same — preserved API contracts, schemas, regulated logic

The AI proposes defaults for each. You override what you want. Don't re-confirm the defaults — keep moving.

05
Stage 3 — Bootstrap the target (~1-3 hours). The refined spec lands in the target folder. forgecraft sets up the cascade tailored to the chosen target stack. The AI generates code under that discipline. T1, T2, T3 done automatically.
06
Verify parity. You now have the new system. Use the harness from Path A's step 6 to drive the new system through the source system's behavioral contracts. Anything that doesn't match is a refinement decision to revisit, not a bug to chase.

If you want a literal port (preserve every wart, change only the stack), say so in step 2 and the AI will skip the refinement conversation entirely. If you want help during the refinement (regulated systems, complex business logic), the Concierge engagement handles the refinement conversation as part of the work.

What you'll have at the end

both paths

Path A — Greenfield

  • A working project. Code, tests, deployment scripts, all derived from a written specification.
  • A specification you can hand to anyone. Use cases, ADRs, behavioral contracts, AI behavioral rules. The next session knows what to do without you in the room.
  • Tier 1, 2, and 3 done. Spec, test harness, deployment infrastructure — all under discipline.
  • An optional path forward. Add features by conversation. Each one tightens the spec.

Path B — Brownfield

  • Two PDF reports. Initial state and final state. Same metrics, side by side. Charts. Receipts.
  • A remediated codebase. Higher scores on the seven properties, regression tests for past bugs, refreshed documentation, better structural discipline.
  • A working harness. Test suite that runs against the running application, not just the code.
  • Optional team-habit report. A separate PDF showing how the team has been operating.
  • Optional Chronicle install. Future sessions inherit what this one learned.
  • Optional new feature. Built under the same discipline so it doesn't break what already works.

Path C — Onboarding

  • An onboarding briefing. 4-8 page markdown file: what this project is, the architecture in one diagram, the conventions to respect, what's surprising, where to start.
  • 2-3 concrete first-task suggestions sized to your role and experience level. Each cites the files involved and rough effort estimate.
  • An architectural cheat sheet. File/folder map, commands, environment setup, "where do I find" answers. Quick reference for week one.
  • Optional team-habit context if you're doing a takeover. Who to trust on which areas, where the recent fires were.

Path D — Migration

  • A working new system in the target folder. Generated under GS discipline from a refined version of the source spec.
  • An ADR trail of migration decisions. What you kept, what you dropped, what you modernized, with rationale. Defensible at the next architecture review.
  • The source system unchanged on its main branch. Migration audit lands on a separate branch in the source repo.
  • Migration-context document. The relevant slice of source-system context the new system needs to know about (legacy data shapes, integration contracts, etc.).
  • Optional parity verification. Run the new system through the source system's behavioral contracts using the harness.

Everything happens on a branch. Your main is untouched until you decide to merge. The AI does not type — you do, but only into the chat.
